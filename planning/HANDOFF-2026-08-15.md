## Goal

Prove host-controlled pause/resume of the Movie Night live channel that every
connected client survives: pause → looping slate + quiet audio, resume →
movie at `pausedAt − 10s`, no client freezes or kicks. This works nowhere
else in the ecosystem (see research doc) — we're building new ground on the
validated "switcher v3" architecture.

## Current state (v0.3.28.0, installed on NAS, **NOT yet tested**)

- Architecture: per-tune persistent ffmpeg = `-fflags +genpts -i
  http://127.0.0.1:8096/MovieNight/stream/feed.ts -c copy -f mpegts pipe:1`
  (raw TS to Jellyfin's tuner). The PLUGIN switches what flows through
  feed.ts: movie feeder (QSV, `-ss <pos>`, lazy-started when the feed gains a
  consumer) vs slate feeder (looping card + 196Hz tone @ 0.15 vol, x264,
  yuv420p, same 720p/AAC shape as the movie feeder for copy-through).
- Driven via admin API: `POST /MovieNight/api/debug/sw2/{golive?itemId=,pause,resume,stop}`,
  `GET .../sw2/status`. Everything logs; feed.ts logs every source
  transition with pids + byte counts.
- Proven so far: movie plays end-to-end through this pipeline (0.3.27 test);
  lazy feeder start = zero backlog, tune lands at live edge.
- NOT proven: the pause/resume swap under `-c copy`. The 0.3.27 (QSV
  re-encode) pause failed with zero slate bytes reaching the switcher —
  0.3.28's chunked/instrumented copy loop targets that; logs will show
  whether the swap delivers now.

## If the copy-swap fails

The feed.ts logs will show one of:
- "source pid X ended after N bytes" but no follow-up "copying from" slate →
  swap logic bug in GetSw2FeederProcess/copy loop ordering.
- Slate bytes flowing but downstream dies → `-c copy` doesn't smooth the
  discontinuity for the remux; fallback = re-encode variant with QSV
  DECODE+encode (`-hwaccel qsv -c:v h264_qsv` input side) or lighter x264,
  and re-measure speed (0.3.27's encode ran 0.68–0.8x — must hold ≥0.98x).
