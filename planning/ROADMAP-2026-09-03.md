# Roadmap — Halloween movie nights (ruled by Jon, 2026-09-03)

**Read this first.** It supersedes `ROADMAP-2026-08-16.md` and the milestone
table in `DESIGN-abr-ladder.md` §9. The design doc stays the reference for the
delivery *mechanism* (custom `ITunerHost` handing clients a direct HLS URL,
sliding window, authed segment route) — the sections it supersedes are listed
in §5 below. Rulings are recorded in `DECISIONS.md` (2026-09-03 entry).

## 1. What changed

Two facts reorder everything that was planned on 2026-08-19:

1. **A deadline.** Halloween movie nights, late September into October 2026.
   First night is roughly three weeks from today.
2. **A different machine.** The plugin runs on Jon's friend's computer (a
   gaming rig, exact hardware TBD — see §6), not the NAS. She is the host and
   controls it. Every encoder measurement in `ITERATION-LOG.md` is about the
   NAS's Intel QSV iGPU and does not transfer. Jon's NAS becomes the **dev and
   test box**; her rig is the **production deploy**.

The requirements, in the host's words: she hits pause, it pauses for everyone
quickly; she hits resume, everyone starts from the same spot; new viewers land
on the live edge. All three are already solved *in principle* by switcher v3
(server-side position clock, slate on pause) plus the ABR-ladder delivery
mechanism (sliding window, no per-client ffmpeg). What is missing is the build.

## 2. Rulings that shape V1 (Jon, 2026-09-03)

| question | ruling |
|---|---|
| adaptive bitrate | **Rung count is a plugin setting** (default 1). Jon's NAS runs one 720p rung; the friend's rig can run several and that gets tested there. |
| top rung | **720p** |
| captions | **Burn-in** for V1, chosen per movie at prep time. WebVTT-over-HLS deferred. |

## 3. Architecture for V1 — and why the rung setting simplifies it

```
 mezzanine.mp4 ──► movie feeder (-re -c copy) ─┐
                                               ├─► feed.ts ─► ENCODER ─► N rungs ─► sliding-window HLS ─► ITunerHost URL ─► clients
 slate (libx264, still + tone) ────────────────┘            (one ffmpeg,                              (direct, no hop)
                                                             N encodes)
```

- **Feeder / slate / feed.ts / pause / position clock: unchanged v3**
  (v0.3.31 behaviour). This is the part the 2026-08-16 acceptance test proved.
- **Encoder: one ffmpeg, `feed.ts` in, N encoded rungs out via
  `var_stream_map`, sliding window.** This is `DESIGN-abr-ladder.md` §4(D) with
  one change: **there is no `-c copy` rung. Every rung is encoded.** Consequences:
  - GOP alignment across rungs is intrinsic (one process, one decoded frame
    stream, one `-g`). The whole M1 "mezzanine must carry a matching fixed GOP"
    constraint, and the 0.22 s drift T2 found on the copy rung, disappear.
  - N=1 is just the degenerate case — the same code path Jon's NAS runs.
  - Cost is N encodes instead of N−1, at 720p and below. On the NAS one QSV
    encode is proven; on a gaming rig several are plausible and get measured
    with the existing `debug/encode-probe` endpoint before anyone relies on it.
- **Encoder backend follows Jellyfin's own hardware-acceleration setting**, as
  `FfmpegCommandBuilder` already maps it: `qsv` (proven on the NAS), `nvenc`
  (exists in code, **never run** — likely what her rig has), `vaapi`, and
  `libx264` as the universal fallback. libx264 at 720p is roughly one core on any
  recent desktop, so a machine with no usable GPU still works at N=1.
- **Mezzanine prep keeps two jobs and loses one.** It still (a) burns in the
  chosen subtitle track and (b) normalises the source to a cheap-to-decode
  720p h264/AAC file so the live encoder is not decoding a 40 Mbps remux. It no
  longer has to produce ladder-aligned GOPs. It is a one-off, ahead-of-time job
  run from the host page ("Prepare"), never at Go Live. Burn-in *must* happen
  here and not in the live encoder: `feed.ts` time ≠ movie time once a pause
  has inserted slate, so subtitle timing can only be applied upstream of the
  feed. Text tracks use the `subtitles` filter; bitmap tracks (PGS/VobSub) use
  `overlay` on the subtitle stream; Jellyfin's `MediaStream` metadata says which.
- **Tuner host: the real thing, replacing the T0 spike.** `Container = "hls"`
  (the value that works — CLAUDE.md gotcha), `RequiresOpening = false`, and an
  **absolute per-client URL** from `IServerApplicationHost.GetSmartApiUrl`
  via `IHttpContextAccessor` — never the hardcoded LAN constant the gate used.
  Remote viewers reach her Jellyfin at whatever public address she uses (§6).
- **Segment route: `[Authorize]`** with the exact-name whitelist (design §4(F),
  milestone M3). The anonymous T0 route is deleted with the spike.
- **Segments live on disk, not tmpfs.** Design §4(E) assumed Linux tmpfs; her
  rig is presumably Windows. ~36 MB resident for three rungs is nothing for an
  SSD. Use a directory under Jellyfin's transcode/cache path.
- **Host surface stays the admin config page** (DECISIONS 2026-08-14: no
  separate host client). She is admin on her own server. It gains a movie
  picker, a subtitle-track dropdown, Prepare, and the existing Go Live /
  Pause / Resume / Stop + status. No item-ID paste box for her.

Settings added (`PluginConfiguration`): `LadderRungs` (1–3, default 1) and a
top-rung bitrate. Rung presets: 720p ~4 Mbps, 480p ~1.5 Mbps, 360p ~0.8 Mbps.
Size the top rung to **her upload bandwidth ÷ expected viewers** — egress is
O(N) with no CDN and is the binding constraint on a home connection.

## 4. Plan (three weeks, four steps)

Test IDs refer to `DESIGN-abr-ladder.md` §8.

### Step 1 — live pipeline through the real tuner host, on the NAS
`M2 + M3 + M4` from the design, collapsed. Encoder with the rung setting (test
at N=1 QSV and N=1 libx264 on the NAS), sliding window, authed route, real
tuner host with per-client URL, T0 spike deleted. Mezzanine prep endpoint (no
UI yet).

**Done when:** Jon tunes Roku + web to the new channel; both `DirectPlay`,
zero server ffmpeg beyond the encoder; a pause reaches both in ≤ ~20 s and a
resume restarts both from the same point (T4, T5). Untune-for-two-minutes-and-
retune lands at the live edge (v0.3.31 behaviour preserved).

### Step 2 — her machine
Install from the manifest, confirm Jellyfin 10.11.x. Run `encode-probe` with
her hardware accel at N=1 and N=3 and record realtime speed. Test from *outside
her LAN* over her public URL on the devices the viewers actually own. Measure
the two things nothing has ever measured: **a new viewer joining mid-broadcast
lands at the live edge**, and **a straggler that falls off the window** (T6 —
does Roku error out, or rejoin?). Pick the rung count from the probe numbers.

**Done when:** two remote devices tune, pause/resume works, and the T6 verdict
is written down.

### Step 3 — host page + prep UI
Movie picker (library search), subtitle-track dropdown, Prepare with progress,
"prepared ✓" state per movie, and the four broadcast buttons. Burn-in verified
on one real film.

**Done when:** she can run prepare → Go Live → pause → resume → stop with no
help from Jon and no curl.

### Step 4 — dress rehearsal
Three to five real friends, real devices, a full-length film, at least a week
before the first night. Fixes land in the remaining days.

**Done when:** the film completes with pause cycles and nobody was kicked off.

### Deferred (not V1)
fmp4 segments; WebVTT selectable captions; a `-c copy` rung (needs the
mezzanine GOP constraint back); per-client `MediaSourceInfo` variation; the
big HLS-machinery deletion (still gated on Jon's ruling, roadmap-08-16 §3);
any host surface outside the dashboard; Android phone app.

## 5. What this supersedes in `DESIGN-abr-ladder.md`

- §4(A): the fixed-GOP constraint on the mezzanine is dropped; burn-in captions
  are added as a prep job.
- §4(D): rung 0 is encoded, not copied; QSV-only args become backend-selected;
  rung count is configurable.
- §4(E): disk directory, not tmpfs.
- §4(G): the load-bearing field is `Container` (`"hls"`), not
  `SupportsTranscoding`; URL must be absolute and per-client.
- §9: replaced by §4 above.
- §10.3 (mezzanine wall-clock): now a host-page "Prepare" job with progress.
